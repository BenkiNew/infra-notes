# Як невдале оновлення перетворилося на «без змін»

Першоджерело: [GitHub Gist](https://gist.github.com/BenkiNew/03f6f203f6709b8102b2e47b7b899d02) · [English version](../en/bash-errexit-hidden-failure.md).

Скрипти: [мінімальне відтворення](../../examples/bash-errexit/bash-errexit-repro.sh), [додаткові контексти](../../examples/bash-errexit/bash-errexit-contexts.sh).

Автор: **Костянтин Банк (ХакерБанк / XAKERBANK)** · [XAKERBANK Labs](https://github.com/BenkiNew) · [DOU](https://dou.ua/users/kostyantin-bank/).

У Bash конструкція `(set -e; generate; compare) || report_failure` може приховати збій `generate`. У цій конструкції subshell стоїть ліворуч від `||`, тому `errexit` усередині нього ігнорується. Якщо виконання доходить до останньої успішної команди, статус блоку буде 0. Це документована семантика Bash, тому пропозиція змінити сам Bash тут не є доречним bugfix PR.

Ця пастка особливо помітна після зміни каталогу даних під systemd `ProtectSystem=strict`: генератор отримує EROFS, наступна перевірка знаходить старі незмінні файли, а журнал повідомляє успіх. Сам приклад нижче відтворює лише проблему керування потоком; він не відтворює mount namespace systemd.

```bash
(set -e; false; printf 'UNCHANGED\n') || printf 'FAILED\n'
```

Блок надрукує `UNCHANGED` і поверне 0. Для критичного кроку перевіряйте результат явно:

```bash
(
  if ! generate; then
    printf 'Generation failed\n' >&2
    exit 1
  fi
  compare
) || report_failure
```

Дозволені `ReadWritePaths` мають включати новий каталог даних і, якщо генератор записує туди тимчасові файли, його робочий каталог. Залишайте `ProtectSystem=strict`; привілейований перезапуск служб можна виконувати окремим вузьким кроком `ExecStartPost` лише за маркером зміни. Такий root-крок має бути вузьким і контрольованим: префікс `+` у systemd означає привілейоване виконання, а не успадкування всіх обмежень непривілейованого синку.

Перевірка включала red/green регресію прихованого статусу помилки, незмінний словник без запиту перезапуску та оновлений словник із запитом перезапуску. Також перевірено, що збій перезапуску зберігає маркер для повторної спроби, а успіх видаляє його. Доданий `bash-errexit-repro.sh` відтворює legacy=0, fixed=1 без даних, мережі чи служб. Це виправлення обробки помилки й конфігурації застосунку; воно не доводить безпомилковість усіх його бізнес-сценаріїв.

Джерело семантики: [GNU Bash: The Set Builtin](https://www.gnu.org/s/bash/manual/html_node/The-Set-Builtin.html).

## Відтворення

Завантажте [bash-errexit-repro.sh](../../examples/bash-errexit/bash-errexit-repro.sh) та запустіть явно через Bash:

```bash
bash --version
bash bash-errexit-repro.sh
```

Очікуваний вивід (рядок помилки йде в stderr; порядок stdout/stderr може відрізнятися):

```text
UNCHANGED (misleading)
Generation failed
legacy=0 fixed=1
```

Сам reproduction завершується зі статусом 0 лише тоді, коли обидва очікувані статуси підтверджені. Приклад `generate`/`compare` вище показує схему виправлення; ці функції не визначені й він не призначений для запуску без реалізації. Виконуваний файл використовує `false` для синтетичного збою.

Перевірено на GNU Bash 5.2.26. Reproduction доводить поведінку керування потоком, а не відтворює весь інцидент або всі версії Bash.

Джерело привілейованого `ExecStartPost` і префікса `+`: [systemd.service](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html#ExecStart=).

## Уточнення після технічного review

Контекст виклику впливає також на shell-функції: `f() { set -e; false; printf 'CONTINUED\n'; }; f || handler` продовжує виконання після `false`. Винесення коду у функцію саме по собі не гарантує зупинку після помилки.

`set -o pipefail` визначає статус pipeline; у цьому прикладі pipeline немає. `trap ERR` має контекстні винятки, подібні до `errexit`; навіть із `set -E` він не перетворює цей блок на надійну перевірку помилки. Конструкція `if ! (set -e; false; printf 'CONTINUED\n'); then handler; fi` теж пригнічує `errexit` у перевірюваному блоці. Явно перевіряйте критичну команду всередині блоку.

У розібраному застосунку loader має `Type=oneshot`, без `RemainAfterExit=yes`: `ExecStartPost` виконується після успішного завершення `ExecStart`. `RemainAfterExit=yes` не є обов'язковим для такого кроку. Для інших типів служб момент запуску `ExecStartPost` визначається їхнім контрактом старту.

За [документацією systemd v257](https://github.com/systemd/systemd/blob/v257/man/systemd.service.xml), `+` обходить для конкретної команди не лише `User=`, `Group=` і `CapabilityBoundingSet=`, а також налаштування файлових namespace, зокрема `PrivateTmp=`. Твердження, що `+` завжди зберігає файлову пісочницю unit, неправильне. Обмеження всього cgroup, наприклад `DevicePolicy=`, не обходяться. Префікс `!` має інший, вужчий контракт щодо user/group credentials.

П'ять описаних тестів не перевіряють паралельні запуски. Один і той самий systemd unit не запускає дві власні activation одночасно, але ручний запуск скрипту чи інший unit може створити конкурентного writer. Для такого сценарію потрібні окрема перевірка й узгоджена серіалізація генерації, встановлення маркера, перезапуску та підтвердження. `RuntimeDirectory=` чи `StateDirectory=` самі по собі не є блокуванням; атомарне перейменування теж не замінює весь протокол. `flock` може бути частиною цього протоколу, якщо всі учасники використовують одне блокування.

Файл `bash-errexit-contexts.sh` перевіряє чотири додаткові випадки без операцій із сервісами. Приклади стосуються перевіреного GNU Bash 5.2.26; це не універсальний контракт інших shell або всіх режимів Bash.
