# Синхронізація успішна, дані застарілі: як Bash і systemd приховали збій після переносу

**Автор:** Костянтин Банк (ХакерБанк / XAKERBANK) · [XAKERBANK Labs](https://github.com/BenkiNew) · **Дата:** 11.10.2026

Опубліковано на [DOU](https://dou.ua/forums/topic/62516/) 11.10.2026; цей текст синхронізовано з публікацією. Першоджерело і скрипти — [GitHub Gist](https://gist.github.com/BenkiNew/03f6f203f6709b8102b2e47b7b899d02), де матеріал мав робочу назву «Як невдале оновлення перетворилося на «без змін»». [English version](../en/bash-errexit-hidden-failure.md).

Скрипти: [мінімальне відтворення](../../examples/bash-errexit/bash-errexit-repro.sh), [додаткові контексти](../../examples/bash-errexit/bash-errexit-contexts.sh).

Після переносу спільного словника в окремий каталог застосунки продовжували працювати, вебсторінки відкривалися, а синхронізація завершувалася повідомленням «без змін». Проте перевірка даних показала: частина нових записів не потрапила до словника.

Причина складалася з двох незалежних механізмів. Обмеження файлової системи в systemd забороняло генератору записувати дані за новим шляхом. А контекст виконання `set -e` у Bash дозволяв скрипту продовжити роботу після помилки й повідомити успіх.

Цей розбір буде корисним тим, хто підтримує Linux-служби, пише Bash-скрипти синхронізації або переносить runtime-дані між каталогами. Нижче — мінімальне відтворення, пояснення причини, виправлення та межі проведених перевірок. Назви служб, шляхи й дані у прикладах вигадані.

## Чому працездатний сервіс не означав актуальні дані

Словник використовували кілька застосунків. Генератор будував його з актуальних даних, а споживачі завантажували результат під час старту процесу.

Після переносу генератор мав записувати файли в новий спільний каталог. Однак споживачі вже мали попередню версію словника, а для частини невідомих форм працювали запасні правила нормалізації. Тому збій оновлення не спричинив повної недоступності сервісів.

Це створило оманливу картину:

- служби працювали;
- сторінки відкривалися;
- попередні дані залишалися доступними;
- синк повідомляв «без змін»;
- нові словникові записи не з'являлися.

Перевірка HTTP-доступності могла підтвердити, що застосунок відповідає. Але вона не могла підтвердити, що його словник відповідає поточному джерелу даних.

Залишкові розбіжності в нормалізації стали приводом перевірити весь шлях: джерело → генератор → файли → завантаження споживачами.

## Перша причина: новий каталог не входив до ReadWritePaths

Loader-служба використовувала `ProtectSystem=strict`. Для її процесів файлова система була переважно доступна лише для читання, а запис дозволявся в явно визначені каталоги.

До переносу генератор працював із дозволеним шляхом. Після переносу каталог даних змінився, а конфігурація служби — ні.

Генератор завершувався з помилкою:

```text
Read-only file system
```

На рівні системного виклику це `EROFS`. Тут важливо відрізняти read-only обмеження від звичайної відмови через права доступу.

Перевірка власника файлу або результат `chmod` не пояснюють усю картину. Процес, запущений у терміналі, і процес, запущений systemd із файловою пісочницею, можуть бачити різні можливості запису за тим самим шляхом.

Спрощена конфігурація виглядала так:

```ini
[Service]
Type=oneshot
User=app
ProtectSystem=strict
ReadWritePaths=/var/lib/example/old-data
```

Після переносу генератор почав записувати в `/var/lib/example/shared-data`. Наявність такого каталогу та правильний власник не додавали його автоматично до `ReadWritePaths`.

Виправлення полягало в оновленні дозволених шляхів. Крім кінцевого каталогу даних, потрібно врахувати робочий каталог генератора, якщо він створює там тимчасові файли.

Вимикати `ProtectSystem=strict` для всього сервісу не знадобилося.

## Друга причина: set -e не зупиняв блок

У скрипті критичний крок був усередині конструкції такого виду:

```bash
(
  set -e
  generate
  compare
) || report_failure
```

Очікування було простим: якщо `generate` повертає помилку, `set -e` зупиняє subshell, після чого виконується `report_failure`.

Але для цієї конструкції очікування неправильне.

Subshell стоїть ліворуч від `||`. У такому контексті Bash ігнорує `errexit` усередині перевірюваного блоку. Виклик `set -e` всередині дужок не повертає очікувану поведінку.

Після збою генератора виконується наступна команда. Вона порівнює файли й бачить, що вони не змінилися. Це правда: невдалий генератор залишив старі файли.

Якщо остання команда завершується успішно, subshell повертає 0. Зовнішній обробник помилки не запускається.

Мінімальне відтворення:

```bash
(set -e; false; printf 'UNCHANGED\n') || printf 'FAILED\n'
```

Блок надрукує `UNCHANGED` і поверне статус 0.

Отже, скрипт плутав два різні стани:

1. Генерація успішна, нові дані тотожні попереднім.
2. Генерація не відбулася, на диску залишилися старі файли.

Порівняння файлів саме по собі не може розрізнити ці стани. Спочатку треба перевірити, чи успішно завершився генератор.

Це документована поведінка Bash, а не новий дефект інтерпретатора. Виправлення потрібне в керуванні потоком застосунку, тому пропозиція змінити сам Bash тут не є доречним bugfix PR.

## Винесення коду у функцію не усуває пастку

Той самий контекст впливає на shell-функції. Наприклад:

```bash
generate_and_compare() {
  set -e
  false
  printf 'CONTINUED\n'
}

generate_and_compare || printf 'HANDLED\n'
```

Функція продовжить виконання після `false` й надрукує `CONTINUED`.

Це важливий нюанс для рефакторингу: поведінка функції залежить не лише від її тіла, а й від контексту виклику. Тому перенесення послідовності команд у функцію та додавання до виклику `|| handler` потребують окремої перевірки обробки помилок.

## Чому pipefail, ERR trap і зовнішній if не виправляють цей випадок

У цій ситуації є кілька привабливих, але недостатніх альтернатив.

### set -o pipefail

`pipefail` змінює спосіб визначення статусу pipeline. У мінімальному прикладі pipeline немає:

```bash
(
  set -e -o pipefail
  false
  printf 'CONTINUED\n'
) || printf 'HANDLED\n'
```

Команда після `false` все одно виконується. `pipefail` корисний для власного завдання, але він не відновлює `errexit` у цьому контексті.

### trap ERR

`ERR` trap має контекстні винятки, подібні до винятків `errexit`. Успадкування trap через `set -E` не означає, що він спрацює для кожної помилки всередині перевірюваного блоку:

```bash
(
  set -eE
  trap 'printf "ERR_TRAP\n"' ERR
  false
  printf 'CONTINUED\n'
) || printf 'HANDLED\n'
```

У перевіреному сценарії друкується `CONTINUED`, а повідомлення trap не з'являється. Trap може бути корисним для журналювання або завершення роботи, але його теж потрібно перевіряти в конкретному контексті виклику.

### if ! на зовнішньому рівні

Інша спроба — перевірити весь блок через `if`:

```bash
if ! (
  set -e
  false
  printf 'CONTINUED\n'
); then
  printf 'HANDLED\n'
fi
```

Це теж перевірюваний контекст: блок продовжує виконання й повертає статус останньої успішної команди.

Проблему усуває явна перевірка критичного кроку всередині блоку.

## Явна перевірка генератора

Виправлена схема:

```bash
(
  if ! generate; then
    printf 'Generation failed\n' >&2
    exit 1
  fi

  compare
) || report_failure
```

Тут статус генератора перевіряється безпосередньо. Після його збою виконується явний `exit 1`, тому порівняння файлів не запускається.

Це схема, а не самостійний виконуваний скрипт: функції `generate`, `compare` та `report_failure` потрібно визначити.

Крім генератора, варто явно перевірити інші критичні операції: отримання початкового стану, читання конфігурації, порівняння результату та створення маркера оновлення. У цьому контексті покладатися лише на `set -e` не слід.

Після виправлення повідомлення «без змін» означає, що генератор успішно виконався, а результат порівняння не виявив оновлення.

## Перезапуск споживачів як окремий крок

Оновити файли недостатньо, якщо споживачі завантажують словник лише під час старту.

У розібраному випадку loader має `Type=oneshot`. Його `ExecStartPost` запускається після успішного завершення `ExecStart`. Для такого використання `RemainAfterExit=yes` не є обов'язковим.

Перезапуск споживачів винесли в окремий крок:

1. Непривілейований синк успішно генерує дані.
2. Якщо файли змінилися, синк створює маркер.
3. Окремий крок перевіряє маркер і перезапускає споживачів.
4. Після успіху маркер видаляється.
5. Якщо перезапуск падає, маркер залишається для повторної спроби.

Для інших типів служб момент запуску `ExecStartPost` визначається їхнім контрактом успішного старту. Не варто переносити пояснення для `oneshot` на всі unit без перевірки.

## Що означає префікс + у systemd

Привілейований крок — окрема межа довіри.

За [документацією systemd v257](https://github.com/systemd/systemd/blob/v257/man/systemd.service.xml), префікс `+` для конкретної команди обходить обмеження, задані через `User=`, `Group=`, `CapabilityBoundingSet=`, а також налаштування файлових namespace, зокрема `PrivateTmp=`.

Тому неправильно вважати, що `+` лише змінює користувача, зберігаючи всі файлові обмеження непривілейованого процесу.

Водночас обмеження, які застосовуються до всього cgroup, наприклад `DevicePolicy=`, не обходяться. Префікс `!` має інший, вужчий контракт щодо user/group credentials. Це не взаємозамінні позначення.

Практично це означає: привілейований helper має бути коротким, контрольованим і виконувати лише потрібну операцію.

## Маркер і конкурентні запуски

Проведені перевірки підтвердили поведінку маркера для послідовного виконання. Вони не доводять коректність за наявності конкурентних writer.

Один systemd unit не запускає дві власні активації одночасно. Проте ручний запуск скрипту або інший unit можуть створити паралельне виконання.

Для такого сценарію простий порядок «перевірити маркер → перезапустити → видалити» потребує окремого аналізу. Наприклад, новий запит на оновлення може з'явитися під час перезапуску, а завершення попередньої операції — видалити спільний маркер.

`RuntimeDirectory=` та `StateDirectory=` організовують каталоги, але самі по собі не блокують конкурентних учасників. Атомарне перейменування також не замінює весь протокол.

`flock` може бути частиною рішення, якщо всі учасники використовують одне блокування. Потрібно узгодити весь цикл: генерацію, встановлення маркера, перезапуск і підтвердження обробки.

У цьому розборі конкурентний сценарій залишається неперевіреним. Твердження про повну надійність механізму за паралельних запусків не робиться.

## Як перевіряли виправлення

Спочатку тест із примусовим збоєм генератора запустили на старому коді. Він відтворив проблему: скрипт повертав 0 замість очікуваного ненульового статусу.

Після виправлення пройшли п'ять синтетичних сценаріїв:

- збій генератора повертає помилку й не повідомляє «без змін»;
- незмінний словник не створює запит перезапуску;
- змінений словник створює маркер;
- збій перезапуску зберігає маркер;
- успішний перезапуск видаляє маркер.

Додатково перевірили можливість запису в дозволені каталоги всередині systemd sandbox. Потім виконали реальну генерацію окремо від повного loader й перевірили стан споживачів після перезапуску.

Окремий набір синтетичних прикладів підтвердив поведінку Bash для функції, `pipefail`, зовнішнього `if !` та `ERR` trap.

Ці перевірки відповідають на різні запитання:

| Перевірка | Що підтверджує |
| --- | --- |
| Мінімальний Bash-приклад | Приховування збою в конкретному контексті |
| Регресійні тести | Правильну обробку помилки та маркера |
| Запис у systemd sandbox | Доступність дозволених шляхів для генератора |
| Реальна генерація | Успішне оновлення словника |
| Перевірка споживачів | Роботу служб після перезапуску |

Жодна з них окремо не доводить коректність усіх бізнес-сценаріїв застосунку.

## Як відтворити поведінку Bash

У репозиторії та у [публічному Gist](https://gist.github.com/BenkiNew/03f6f203f6709b8102b2e47b7b899d02) є два виконувані синтетичні файли:

- [bash-errexit-repro.sh](../../examples/bash-errexit/bash-errexit-repro.sh) — початковий приклад і виправлена перевірка;
- [bash-errexit-contexts.sh](../../examples/bash-errexit/bash-errexit-contexts.sh) — чотири додаткові контекстні сценарії.

Завантажте файли та запустіть їх явно через Bash:

```bash
bash --version
bash bash-errexit-repro.sh
bash bash-errexit-contexts.sh
```

Очікуваний вивід `bash-errexit-repro.sh` (повідомлення помилки йде в stderr, тому порядок рядків stdout/stderr може відрізнятися):

```text
UNCHANGED (misleading)
Generation failed
legacy=0 fixed=1
```

Очікуваний вивід `bash-errexit-contexts.sh`:

```text
PASS: function
PASS: pipefail
PASS: outer_if
PASS: err_trap
```

Перший reproduction підтверджує `legacy=0 fixed=1`. Сам тестовий скрипт повертає 0 лише тоді, коли обидва очікувані статуси підтверджені. Contexts-скрипт повертає 0 лише тоді, коли всі чотири сценарії надрукували `CONTINUED` зі статусом 0. Обидва файли синтетичні: без даних, мережі, запису файлів і операцій із службами.

Приклади перевірено на GNU Bash 5.2.26. Вони не відтворюють systemd mount namespace та не є універсальним контрактом для інших shell або всіх режимів Bash.

## Що варто винести з цього випадку

Після переносу недостатньо перевірити, що процес працює та сторінка відповідає. Для систем із похідними даними потрібна окрема перевірка їхньої свіжості.

Зміна каталогу даних також потребує перевірки середовища служби: дозволених шляхів, тимчасових файлів і способу завантаження результату споживачами.

Нарешті, `set -e` не замінює явну перевірку критичних операцій. Особливо коли команди виконуються всередині функції або subshell, статус яких перевіряється через `||`, `if` чи `!`.

У цьому випадку старі файли справді були «без змін». Помилка полягала в тому, що цей факт використали як доказ успішної генерації.

## Джерела та межі

- [GNU Bash: The Set Builtin](https://www.gnu.org/s/bash/manual/html_node/The-Set-Builtin.html) — семантика `set -e` і контексти, у яких `errexit` ігнорується.
- [GNU Bash: Bourne Shell Builtins](https://www.gnu.org/software/bash/manual/html_node/Bourne-Shell-Builtins.html) — `trap` і контекстні винятки `ERR`.
- [systemd v257: systemd.service](https://github.com/systemd/systemd/blob/v257/man/systemd.service.xml) — префікси команд `+` і `!`, `ExecStartPost`, `Type=oneshot`.
- [systemd.exec](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html) — `ProtectSystem=`, `ReadWritePaths=`, `RuntimeDirectory=`, `StateDirectory=`.

Приклади узагальнюють наш випадок із вигаданими назвами служб і шляхами. Перевірки підтверджують керування потоком у Bash, конфігурацію файлової пісочниці systemd та обробку маркера. Вони не доводять коректність усіх бізнес-сценаріїв застосунку і не є універсальним контрактом для інших shell, версій Bash або типів служб.
