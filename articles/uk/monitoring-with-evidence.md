# Як моніторинг помиляється: стара помилка, вимкнений сервіс і недоступна перевірка

**Автор:** Костянтин Банк (ХакерБанк / XAKERBANK) · [XAKERBANK Labs](https://github.com/BenkiNew) · **Дата:** 08.10.2026

Адаптовану версію опубліковано на [DOU](https://dou.ua/forums/topic/62492/) 10.10.2026. Тут збережено розширений розбір.

У моніторингу двох Linux-серверів ми зіткнулися з проблемою: показник міг бути технічно правильним, а висновок із нього — неправильним. У журналі справді була помилка. Служба справді не працювала. Лічильник справді містив нуль. Але це ще не означало поточний інцидент, несправну службу або відсутність помилок.

Нижче — три пастки з нашого досвіду та спосіб перевіряти їх. Назви служб, час і числові приклади змінені. Це опис підходу, а не універсальний алгоритм для будь-якої системи.

## 1. Помилка в журналі стала постійною аварією

Служба один раз отримала timeout. Пізніше вона відновила роботу, але файл, у який потрапив timeout, не отримував нових записів. Колектор знаходив слово `error` і кожного разу показував червоний статус.

Запис не був вигаданий. Неправильною була його інтерпретація як поточної проблеми.

Ми стали перевіряти разом:

- коли виникла помилка;
- поточний стан і результат роботи служби;
- чи є підтверджена успішна активність після помилки;
- наскільки свіжі самі спостереження.

Для конкретної постійно працюючої служби історичну помилку відокремили від активної: потрібні були `ActiveState=active`, `Result=success` і новіша підтверджена активність. Додали поріг віку помилки. Цей поріг є локальним правилом для цієї служби, а не загальною властивістю systemd.

Важлива деталь: повідомлення про перезапуск або будь-який новий рядок у журналі не обов'язково означає, що програма відновила свою основну функцію. Для імпортера це може бути успішний імпорт, для API — коректна відповідь, для реплікації — підтверджений стан і допустимий лаг.

Інша ситуація — збережений `failed` у systemd. Стан помилки може залишатися після невдалого запуску, навіть якщо конфігурацію вже виправили. Це підтверджує факт невдалого запуску, але саме по собі не доводить, що причина досі існує. Водночас виправлений файл конфігурації не доводить відновлення: потрібен новий успішний запуск або інша відповідна перевірка.

Корисні команди для служби з умовною назвою `example-worker.service`:

```bash
systemctl show example-worker.service \
  -p LoadState -p ActiveState -p SubState -p Result \
  -p ExecMainStatus -p ExecMainExitTimestamp

journalctl -u example-worker.service \
  --since '24 hours ago' --no-pager
```

Окремо перевірте, що користувач колектора має доступ до потрібного журналу. Успішне виконання команди не завжди гарантує повне охоплення журналів системи.

`systemctl reset-failed` очищає збережений стан помилки та відповідні лічильники. Воно не перевіряє програму і не виправляє причину збою. Використовувати цю команду як доказ відновлення не можна.

## 2. Вимкнену обробку показували як справну

Власник вимкнув одну з фонових обробок. Джерельні файли та старі результати залишилися на місці. Моніторинг продовжував читати останній успішний результат і показував його так, ніби обробка працює зараз.

Ми розділили два факти:

1. Обробка зараз вимкнена за рішенням власника.
2. Остання виконана перевірка колись завершилася успішно.

У поточному статусі показали «вимкнено власником». Старий успішний результат залишили історією. Зупинена обробка більше не мала виглядати як чинна перевірка даних.

Приклад запису нижче вигаданий; назви полів — приклад для власного колектора, а не API systemd:

```json
{
  "processing": {
    "desired_state": "disabled",
    "observed_state": "inactive",
    "reason": "owner_decision"
  },
  "last_check": {
    "status": "success",
    "checked_at": "2026-09-01T08:00:00Z"
  }
}
```

Саме `disabled` у systemd не є достатнім доказом рішення власника. Вимкнений для автоматичного запуску юніт може працювати зараз або запускатися вручну. Джерело очікуваного стану потрібно визначити окремо: конфігурація, керований прапорець або задокументоване рішення.

Так само `inactive` не завжди означає збій. `Type=oneshot` без `RemainAfterExit=yes` після успішного виконання зазвичай не залишається в стані `active`. Для періодичного завдання важливі останній результат, час завершення, очікуваний розклад і результат роботи.

## 3. Недоступну перевірку перетворили на нуль помилок

Колектор не зміг прочитати потрібні дані. Замість статусу «не перевірено» повернувся нуль.

На дашборді ці дві ситуації виглядали однаково:

- перевірили джерело й не знайшли помилок;
- джерело не прочитали.

Це особливо підступно в shell-коді з fallback на кшталт «якщо команда не вдалася, надрукувати 0». Він робить результат зручним для обробки, але приховує невдалу перевірку.

Для недоступного джерела результат має зберігати невідоме значення:

```json
{
  "status": "unavailable",
  "error_count": null,
  "reason": "journal_access_denied"
}
```

Для успішної перевірки без знайдених помилок:

```json
{
  "status": "complete",
  "error_count": 0,
  "window_start": "2026-09-01T00:00:00Z",
  "window_end": "2026-09-02T00:00:00Z"
}
```

Якщо перевірка завершена лише частково, потрібен окремий стан `partial` і опис охоплення. Знайдений нуль у перевіреній частині не можна видавати за нуль у всьому джерелі.

Недоступність перевірки також не доводить несправність самої програми. Це окрема проблема спостереження, яка потребує власного пояснення.

## Що ми стали показувати замість одного кольору

| Ситуація | Що показувати | На чому ґрунтується висновок |
| --- | --- | --- |
| Підтверджена поточна помилка | Поточний інцидент | Свіжі дані та перевірка відповідної функції |
| Стара помилка, після якої підтверджено відновлення | Історична помилка | Час помилки та новіше підтвердження відновлення |
| Обробку вимкнув власник | Вимкнено власником | Відомий очікуваний стан та фактичний стан |
| Джерело недоступне колектору | Не вдалося перевірити | Причина недоступності, значення `null` |
| Перевірено частину джерела | Часткова перевірка | Явні межі охоплення |
| Старий успішний snapshot | Застарілі дані | Час збору та допустимий вік спостереження |

Ці назви — наші домовленості для колектора й інтерфейсу. Вони не замінюють системні статуси й не є гарантією відсутності інших проблем.

## Як перевірити власний дашборд

Перевірку можна почати з трьох сценаріїв у тестовому середовищі:

1. Залишити старий запис про помилку, після якого є підтверджене успішне виконання. Перевірити, чи дашборд розрізняє історію та поточний стан.
2. Позначити періодичне завдання як свідомо вимкнене, зберігши старий успішний результат. Перевірити, чи історичний результат не видається за свіжу перевірку.
3. Зробити джерело недоступним саме тестовому колектору. Перевірити, чи з'являється причина недоступності, а не нуль помилок.

Для кожного сценарію потрібен передбачуваний результат у даних колектора й відповідний текст в інтерфейсі. Якщо backend повертає `null`, а frontend перетворює його на `0`, помилка лишається.

Не потрібно заради такого тесту зупиняти production-служби, змінювати права на робочі журнали чи очищати історію. Використовуйте тестовий юніт, окремий журнал або штучний snapshot.

Ми не прибрали помилки з історії. Ми перестали видавати старі та неповні спостереження за відповідь на запитання «що відбувається зараз». Це зробило моніторинг кориснішим для рішень про наші сервери.

## Джерела та межі

- [systemctl](https://www.freedesktop.org/software/systemd/man/latest/systemctl.html): `show`, `status`, `reset-failed`.
- [systemd.service](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html): `Type=oneshot`, `RemainAfterExit`.
- [journalctl](https://www.freedesktop.org/software/systemd/man/latest/journalctl.html): фільтрування журналу й права доступу.

Семантику systemd звірено також із локальними man-сторінками під час підготовки матеріалу. Практичні приклади узагальнюють нашу реалізацію моніторингу. Стаття не встановлює універсальних порогів свіжості та не стверджує, що `active` або `Result=success` самі по собі доводять справність програми.
